# Q8_0 exact GEMV の変種スイープ実測（2026-10-15, A100-SXM4-80GB）

`tests/qwen38_hc_pipe_bench.cu` を拡張し、**本番カーネルそのもの**を
形ごとに全変種で計測した（すべて参照スカラーカーネルと bit 比較、全ケース bit-ok）。
実行: `nvcc -O3 --use_fast_math --extra-device-vectorization -std=c++17 -arch=sm_80 -Isrc`

変種: スカラー参照 / 非パイプ dp4a / PIPE=4,8,16,32,64 / chunk-split=1,2,4,8（新規実験）。

## 2. 否定できた 2 つの仮説（実測）

1. **深いパイプラインは効かない。** PIPE=32/64 は大形で 273/199 GB/s まで落ちる。
   PIPE 段の先読みがレジスタを食い、occupancy と warp 数が落ちるため。
   Task V の「大きい形では PIPE が負ける」という判断は正しく、現行の形状しきい値が最適。
2. **行の chunk を複数 warp に分割しても効かない。** split=2/4/8 は全形で単調に悪化
   （qsa qkv 23.0 → 42.9 → 67.0 → 125.3 us）。chunk 分割は warp 数を増やすが、
   各 warp が同じ 34 バイトブロックの一部だけを読むため**ロード命令数とセクター要求が
   分割数だけ増え**、MLP の改善を打ち消す。bit 一致は全分割で成立した（加算順は不変）。

## 3. なぜ 26% で止まるのか（ncu カウンタ）

ncu（`gpu__time_duration.sum`, `dram__bytes_read.sum`, 各 throughput）で測ると:

| shape | warp 数 | us | DRAM 読 | dram% | sm% | l1tex% |
|---|---:|---:|---:|---:|---:|---:|
| hc down 320x10240 (PIPE=16) | 320 | 40.9 | 3.52 MB | 4.4 | 14.1 | 11.2 |
| hc up 10240x320 (dp4a) | 10240 | 13.6 | 3.49 MB | 13.4 | 41.4 | 38.2 |
| gdn z 6144x2560 (dp4a) | 6144 | 77.6 | 16.72 MB | 15.2 | 28.8 | 30.1 |
| gdn out 2560x6144 (dp4a) | 2560 | 49.0 | 16.72 MB | 24.3 | 44.1 | 46.3 |
| shexp gate/up 640x2560 (PIPE=16) | 640 | 16.3 | 1.76 MB | 5.7 | 19.0 | 15.8 |

- DRAM の実増幅は **1.26 倍**（3.52 MB 読んで 2.79 MB 有用）で、**セクター増幅は主因ではない**。
- どのパイプも 50% 未満。つまり **帯域でも命令発行でもなく、遅延を隠す並列度（warp 数 × 先行ロード数）
  が律速**。1 warp = 1 行、有効レーンは 8/32 本、行内は逐次チェーンという構造上、
  行数が少ない形（320 行など）は 3 warp/SM しか立たず、そのまま遅延が露出する。
- 上記の 2 つの実験は、この並列度を「レジスタ（PIPE）」でも「分割（split）」でも
  上げられないことを示している。次に試す価値があるのは行を shared に **cp.async で
  先読み**する方式（レジスタを食わずに MLP を増やす）だけ。

---

## 4. 結論

現行の Q8_0 exact GEMV は、**この重みレイアウト（Q8_0 = 34 バイトブロック、行内逐次 F32 チェーン）
のもとで、試した全変種の中で最速**です。これ以上の速度は加算順を変えない限り
カーネル構造の作り替え（cp.async staging / 複数行の同時処理）でしか出ません。
